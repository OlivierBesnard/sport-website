# sport-website — CMS modulaire auto-hébergé pour clubs de sport

Chaque club installe sa propre instance (site public + back-office). Les fonctionnalités s'ajoutent par modules, qui communiquent via des événements du noyau. Les instances se mettent à jour automatiquement à chaque release GitHub.

Le plan complet est dans `docs/PLAN.md` et le découpage en étapes dans `docs/BACKLOG.md`. Ces fichiers sont **locaux** : `/docs` est ignoré par Git et le dépôt est public. Ne jamais les forcer dans un commit.

## Stack (cf. PLAN §6.2)

- Node.js 24, pnpm 10 (workspaces), Turborepo, TypeScript strict, ESM uniquement
- Serveur : Hono (`@hono/node-server`), rendu serveur React 19 des pages
- Back-office : SPA React (Vite), Tailwind, shadcn/ui ; éditeur de pages Puck
- Base : SQLite (`better-sqlite3`) + Drizzle ORM, migrations drizzle-kit
- Auth : Better Auth ; validation : zod
- Lint et format : Biome ; tests : Vitest (+ Playwright pour le bout en bout)

## Structure

- `apps/` : `server` (site public, API, webhooks, tâches), `admin` (back-office + éditeur), `supervisor` (mises à jour automatiques)
- `packages/` : `config`, `core`, `db`, `module-sdk`, `module-loader`, `blocks`, `themes`, `ui`
- `modules/` : modules officiels, inclus dans la distribution
- `deploy/` : Docker, compose, paquets d'installation

## Commandes

- `pnpm install`
- `pnpm check` : lint + typecheck + tests. Avant chaque commit, lancer `pnpm check` puis `pnpm build` en local : les deux doivent passer.
- `pnpm lint` : Biome en vérification (lint, formatage, ordre des imports) ; `pnpm format` : Biome applique formatage et corrections sûres
- `pnpm typecheck` : `tsc --noEmit` dans chaque paquet (Turborepo) et sur les fichiers TypeScript de la racine
- `pnpm test` : Vitest lancé à la racine, un projet par paquet de `apps/*`, `packages/*`, `modules/*`
- `pnpm test:e2e` : tests de bout en bout Playwright (dossier `e2e/`, config `playwright.config.ts`) sur le serveur compilé : construit d'abord tout le monde (`turbo run build`), lance le serveur avec des données neuves via `webServer`, navigateur Chromium (`pnpm exec playwright install chromium` ; si le téléchargement échoue, passer le projet sur `channel: "msedge"` pour utiliser le Edge local, sous Windows).
- `pnpm build` : Turborepo (`tsc -p tsconfig.build.json` vers `dist/` pour les paquets)
- `pnpm db:generate --name <nom>` : après une modification du schéma (`packages/db/src/schema`), génère la migration SQL (drizzle-kit) dans `packages/db/migrations`, à commiter avec le schéma. Un test échoue si schéma et migrations divergent.
- `pnpm --filter @sport-cms/server dev` : serveur lancé depuis les sources (`tsx watch` avec la condition `@sport-cms/source` et `apps/server/tsconfig.dev.json`, qui étend la transformation JSX aux sources des autres paquets), sans build. `start` lance `dist/main.js` (après `pnpm build`). `seed:demo` ajoute les pages de démonstration dans la base de `DATA_DIR` ; jamais appelé par le serveur. Avec `--filter`, le dossier courant est `apps/server`, donc `DATA_DIR` vaut par défaut `apps/server/data`.

## Conventions

- Identifiants et commentaires du code en anglais ; textes visibles par les utilisateurs en français ; messages de commit en français.
- Chaque fonctionnalité arrive avec ses tests. Ne jamais désactiver un test ou une règle de lint pour faire passer la vérification. Seule exception : une suppression ponctuelle (`biome-ignore`) sur une ligne précise, avec la justification dans le commentaire, et signalée au relecteur.
- Pas de dépendance sans nécessité ; `pnpm-lock.yaml` toujours à jour. Les scripts d'installation des dépendances sont déclarés dans `allowBuilds` (`pnpm-workspace.yaml`) et autorisés seulement s'ils sont indispensables (`better-sqlite3` fournit ses binaires précompilés).
- Aucun secret dans le code ni dans les tests : les clés de test sont générées à la volée.
- Développement sous Windows, exécution sous Linux (image Docker) : scripts multiplateformes uniquement (pas de `rm -rf`, de variables d'environnement inline ni de chemins en dur avec `\` ou `/`). Fins de ligne LF partout (normalisées par `.gitattributes` ; Biome les vérifie aussi dans le code, le JSON et le YAML).
- Paquets internes : `tsconfig.json` étend `@sport-cms/config/tsconfig.base.json`, `tsconfig.build.json` étend `@sport-cms/config/tsconfig.build.json`. Dans `package.json`, `exports["."]` déclare en premier la condition `"@sport-cms/source": "./src/index.ts"`, puis `types` et `default` vers `dist/` ; une sous-entrée (ex. `exports["./config"]`) suit le même modèle. L'entrée racine d'un paquet utilisable dans le navigateur n'importe aucun module Node (`node:*`) : le code réservé au serveur passe par une sous-entrée. L'exécution et TypeScript utilisent `dist/`, que Turborepo construit pour les dépendances avant `typecheck` et `build`. Les tests, eux, activent la condition `@sport-cms/source` (`ssr.resolve.conditions` dans `vitest.config.ts`) : ils importent toujours les sources, jamais un `dist/` absent ou périmé.
- Données d'exécution dans `DATA_DIR` (par défaut `./data`, ignoré par Git, comme `apps/*/data`) ; la base est `DATA_DIR/database.sqlite` (`databasePath(dataDir)` de `@sport-cms/db`).
- Configuration d'exécution : `parseRuntimeConfig(env)` de `@sport-cms/core/config` (zod) lit `DATA_DIR`, `PORT`, `BASE_URL` et `SECRET_KEY` dans l'objet reçu (`process.env` en production, un objet littéral dans les tests).
- JSX : `jsx: "react-jsx"` dans la configuration TypeScript partagée ; `tsc` compile les `.tsx` vers `dist/`, Vitest les transforme directement. Un paquet utilisable dans le navigateur ajoute `"lib": ["es2025", "dom"]` (ex. `blocks`).
- Serveur (`apps/server`) : seul le point d'entrée lit `process.env` ; `main.ts` appelle `bootInstance(env)` (`src/boot.ts`) : `openInstance(env)` (`parseRuntimeConfig`, puis base `DATA_DIR/database.sqlite` ouverte et migrée), chargement des modules, puis l'application avec toutes ses routes ; `bootInstance` est testé directement (un redémarrage = un second appel sur le même `DATA_DIR`). Tout le reste reçoit ses dépendances : `createApp({ db, baseUrl, secretKey, htmlCache?, blocks?, theme?, logger?, routes? })`, testé avec `app.request()`. `SECRET_KEY` est requise pour démarrer : sans elle `bootInstance` lève `StartupError` (message en français, base refermée) et le serveur s'arrête. Le cache HTML (`HtmlCache`) ne garde que des pages publiées ; toute modification visible d'une page doit appeler `htmlCache.invalidate(chemin)`, et un changement global (thème, modules activés…) `clear()`. Un rendu prend un ticket (`htmlCache.ticket(chemin)`) **avant** de lire la page et le passe à `set(chemin, html, ticket)` : compteur de génération par chemin (relevé par `invalidate`) et époque globale (relevée par `clear`), si bien qu'un rendu commencé avant une invalidation ne réinsère jamais une page périmée. `bootInstance` crée **un seul** `HtmlCache` et **un seul** registre de blocs (`modules.blocks()` du `ModuleHost`), passés à la fois à `createApp` et aux API admin (`pagesApiRoutes`, `navigationApiRoutes`, `modulesApiRoutes`) : une publication du back-office invalide exactement le cache que le site public lit, et un nouveau registre viderait tout le cache à chaque requête.
- Pages : contenu au format de données de Puck (`{ root, content, zones }`, blocs `{ type, props: { id, … } }`, blocs imbriqués dans les champs `slot`). Chemins toujours sous forme canonique : `normalizePagePath` de `@sport-cms/core` (NFC, sans `/` final sauf `/`, sensible à la casse) à l'écriture comme à la lecture ; les variantes sont redirigées (301).
- API admin des pages (`apps/server/src/pages-api.ts`, sous `/api/pages`, `requirePermission("pages.edit")`) : `GET /api/pages` (liste), `POST` (création : chemin normalisé, titre requis, préfixes réservés refusés — `/health`, `/assets`, `/admin`, `/api`, `/hooks`, `/media` —, unicité → 409). Le chemin de la page passe **toujours en paramètre de requête** `path` (encodé, `encodeURIComponent`), l'action dans le chemin de l'URL — aucune ambiguïté pour l'accueil `/` ni pour une page nommée `/publish` ou `/equipe/versions` ; sans `path` → 400 : `GET /api/pages/page?path=…` (brouillon + métadonnées), `PUT /api/pages/page?path=…` (brouillon `{ root, content, zones }` + colonnes facultatives `title`/`seo` ; valide les blocs : racine limitée à Hero et Section, `allow`/`disallow` de chaque emplacement respectés (`slotAccepts` de `@sport-cms/blocks` : pas de Colonnes dans des Colonnes, ni de Section ou d'Héro dans une Section), texte alternatif requis sur toute image informative — champ `decorative` coché excepté), `DELETE /api/pages/page?path=…`, `POST /api/pages/publish?path=…`, `POST /api/pages/unpublish?path=…`, `GET /api/pages/versions?path=…`, `POST /api/pages/restore?path=…` (restaure une version comme brouillon), `POST /api/pages/rename?path=…` (nouveau chemin dans le corps). Réponses 400 en français avec `fields` mappant chaque chemin de bloc fautif (`content.2.alt`…). Le client de l'admin construit ces URL avec `pageUrl(action, chemin)` (`apps/admin/src/api/pages.ts`).
- Contrôle d'origine des API (`apps/server/src/same-origin.ts`, posé par `createApp` sur `/api/*` avant les routes) : toute requête non GET/HEAD/OPTIONS dont l'en-tête `Origin` est présent et différent de l'origine de `baseUrl` (y compris `Origin: null`) → 403 en français ; sans `Origin` (curl, script) elle continue vers les contrôles de session. `/api/auth/*` reste au contrôle propre de Better Auth (mêmes règles, ses codes d'erreur). Le même endroit pose `bodyLimit` de Hono sur `/api/*` (`MAX_API_BODY_BYTES`, 4 Mo : au-delà 413 en français).
- Publication : la copie du brouillon vers `published_data` voit ses `root.props` **résolus et figés** (titre toujours présent : champ racine, sinon `seo.title`, sinon colonne `pages.title` ; description et image : champ racine, sinon colonnes `pages.seo`, sinon absents) par `buildPublishedSnapshot` — c'est le tranchage du report E03 : le repli est versionné dans le snapshot, et `findPublishedPage` ne lit les colonnes en direct que pour les pages publiées avant cette règle (données sans `root.props.title`). Modifier le brouillon ou les colonnes sans republier ne change donc rien au site public. Chaque publication ajoute une ligne `page_versions` (version = max + 1, mêmes données que le snapshot), fixe `published_at`, invalide le cache HTML de la page et écrit `pages.published` dans l'audit ; la dépublication, le renommage (ancien et nouveau chemin) et la suppression aussi (`pages.unpublished`, `pages.renamed`, `pages.deleted`, et `pages.restored` pour une restauration). Quand une entrée de menu pointe vers la page, son lien figure sur toutes les pages : renommage, suppression, dépublication et première publication (ou republication après dépublication) vident alors **tout** le cache (`clear()`) au lieu des seules entrées de la page. La publication exige exactement un titre de niveau 1 (`countLevel1Headings` : blocs Titre de niveau 1 non vides + Héros avec un titre, comptés dans tout l'arbre) et refuse sinon (400, message français).
- Blocs (`@sport-cms/blocks`) : `defineBlock({ type, label, fields, defaultProps, render })`, champs au format Puck (`text`, `textarea`, `richtext`, `number`, `boolean`, `select`, `radio`, `slot`, `array`, `object` — le `boolean` n'existe pas chez Puck : l'éditeur le présente comme une radio Oui/Non, la valeur stockée reste un booléen). Le type des props décide des champs possibles (`FieldFor`, `Fields<Props>`) : `Slot` → `slot`, `RichText` → `richtext`, `string` → `text`/`textarea`/`select`/`radio`, union de littéraux → `select`/`radio` avec ces seules valeurs, `number` → `number`/choix, `boolean` → `boolean`/choix, liste d'objets → `array` (champs des éléments typés), objet → `object` ; un champ incohérent est une erreur de compilation (tests `@ts-expect-error` de `types.test.tsx`). Le rendu public (`renderPageContent`, entrée `@sport-cms/blocks/server`) ignore les types inconnus (bloc d'un module désactivé compris, sans erreur), isole chaque bloc dans sa propre frontière `Suspense` (une erreur levée par `render` **ou** par un composant enfant pendant le rendu React n'écarte que ce bloc et ses blocs imbriqués ; elle est signalée à `onBlockError` — l'erreur de `render`, ou une `BlockComponentError` pour un composant, le rendu serveur synchrone ne transmettant pas l'erreur d'origine — et la page n'est alors pas mise en cache (rendue à chaque requête, mais chaque échec n'est journalisé qu'une fois par page jusqu'au prochain `invalidate` de la page ou `clear` du cache) ; `renderToStaticMarkup` ne laisse aucun marqueur dans le HTML), remplace les valeurs invalides par les valeurs par défaut et assainit les champs `richtext` (sanitize-html, liste blanche) : c'est le seul endroit où du HTML saisi atteint la page, et le seul `biome-ignore` admis (règle `noDangerouslySetInnerHtml` du domaine React de Biome, activé dans `biome.json`). Les URL saisies passent par `safeLinkUrl` (liens : `http(s)`, `mailto:`, `tel:`, relatifs) / `safeImageUrl` (images : `https://` absolu ou chemin commençant par un seul `/`) ; toute barre oblique inverse est refusée.
- Modules — SDK (`@sport-cms/module-sdk`, entrée racine sans Node) : `defineModule({ id, name, version, description?, category?, engines?: { cms }, permissions?, dataProcessing?, settings?, credentials?, blocks?, lifecycle?: { onEnable?, onDisable? } })` (réglages et identifiants : schémas zod ; `permissions` : accès demandés au propriétaire, `members:write`… ; `dataProcessing` : déclaration RGPD), `defineBlock` et les types de blocs réexportés de `@sport-cms/blocks`, contexte `ModuleContext` (`ctx.module`, `ctx.logger`, `ctx.settings()`, `ctx.credentials()`, `ctx.kv.get/set/delete`, tout asynchrone, limité au module). Validation : `parseModuleManifest` (`manifest.json`, `engines.cms` requis) et `checkModuleDefinition` (export par défaut : forme, schémas zod, fonctions, types de blocs préfixés par `<id>.`, sans espace, uniques), messages en français (locale `fr` de zod passée à chaque validation, sans toucher la configuration globale de zod). Identifiant : `MODULE_ID_PATTERN` (minuscules, chiffres, tirets). Version du CMS : `CMS_VERSION` de `@sport-cms/core` (semver, à tenir alignée par le script de release, E13).
- Modules — chargement (`@sport-cms/module-loader`, Node uniquement) : `loadModules({ official, modulesDirectory, cmsVersion?, reservedBlockTypes?, logger? })` au démarrage : modules officiels (`modules/*`, listés dans `apps/server/src/official-modules.ts` et dépendances de `@sport-cms/server`), puis un dossier par module installé dans `DATA_DIR/modules/<id>/` (`manifest.json` + `server.js` ESM, importé dynamiquement, sans compilation ; pris en compte au démarrage suivant). Le manifeste est lu et vérifié **avant** tout code (identifiant = nom du dossier, `engines.cms` satisfait par `semver`, préversions comprises) ; l'export par défaut de `server.js` doit ensuite être une définition valide de même id et version (au-delà de 10 s sans fin de chargement, le démarrage continue sans lui : le code n'est pas interrompu, et un module qui bloque le thread bloque le démarrage). Le manifeste fait foi pour ce qu'affiche l'instance (nom, permissions, RGPD). Tout refus (manifeste, définition, incompatibilité, code qui plante, identifiant ou type de bloc déjà pris, noyau compris) est journalisé (`Module « id » refusé : …`), listé dans `failures`, et le serveur démarre sans le module. Dépendances partagées : un module installé importe `react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `zod` et `@sport-cms/module-sdk` depuis le CMS (hook de résolution `module.registerHooks`, limité aux fichiers sous `DATA_DIR/modules`, chemin donné et chemin réel — `realpathSync` — pour un `DATA_DIR` atteint par un lien, une jonction ou un nom court 8.3 : une seule copie de React, ses hooks fonctionnent) ; il embarque toute autre dépendance. Vitest charge ces fichiers nativement comme en production (`server.deps.external` de `vitest.config.ts`, motif `modules/<id>/<fichier>.js`). Fixture de test : `writeModuleFixture` de `@sport-cms/module-loader/testing`.
- Modules — état (`ModuleHost`, construit par `bootInstance`) : chaque module chargé a sa ligne `modules` (désactivé au départ, version mise à jour à chaque nouvelle version) ; une ligne dont le module n'est plus chargé est conservée avec ses données (`status: "unavailable"`). `blocks()` = blocs du noyau + blocs des modules activés et chargés, même objet tant que rien ne change. Activer : réglages enregistrés valides selon le schéma, puis `onEnable(ctx)` (une erreur laisse le module désactivé), puis `enabled = 1` et audit `modules.enabled` (version et permissions accordées) ; désactiver : `enabled = 0` et audit `modules.disabled`, puis `onDisable` (erreur seulement journalisée) ; pendant une activation ou une désactivation en cours, toute autre opération sur le module (y compris celles qui ne changeraient rien) → `busy`. Les erreurs de validation des schémas des modules sont en français (locale `fr` de zod, par validation) ; `ctx.settings()` et `ctx.credentials()` repassent la valeur enregistrée au schéma (erreur française si elle ne le respecte plus). Réglages : validés par le schéma du module, stockés après parsing (valeurs par défaut appliquées), audit `modules.settings_updated` (noms des clés). Identifiants : validés puis chiffrés AES-256-GCM (`CredentialCipher` : clé dérivée de `SECRET_KEY` par HKDF-SHA256, IV aléatoire, identifiant du module en données authentifiées, format `v1:<iv>:<tag>:<chiffré>` en base64url), une valeur par module dans `module_credentials`, **jamais renvoyés** (seulement `configured`, `fields`, `updatedAt`) ni écrits dans l'audit (`modules.credentials_updated` avec les noms des champs, `modules.credentials_deleted`). Pas de migration : les tables `modules`, `module_credentials` et `module_kv` existent depuis E02.
- API admin des modules (`apps/server/src/modules-api.ts`, sous `/api/modules`, `requirePermission("modules.manage")`) : `GET /api/modules` (`{ modules, failures }` : chaque module avec source, statut, état, permissions, RGPD, blocs, réglages, `settingsSchema` en JSON Schema pour le formulaire d'E08, état des identifiants, raison du refus), `GET /api/modules/:id`, `POST /api/modules/:id/enable` et `/disable` (vident **tout** le cache HTML quand le registre change), `PUT /api/modules/:id/settings` (corps : l'objet des réglages), `PUT /api/modules/:id/credentials` (corps : l'objet des identifiants), `DELETE /api/modules/:id/credentials`. Réponses `{ module }` ; erreurs en français : 400 `{ error, fields }`, 404 module inconnu, 409 module non chargé ou opération en cours, 500 si le hook du module a échoué. Module officiel de démonstration : `modules/exemple` (`@sport-cms/module-exemple` : bloc `exemple.citation`, réglage `signature`, identifiant `apiKey`, `onEnable` qui compte les activations dans `ctx.kv`).
- Site public : CSP stricte (aucun script, aucun attribut `style`, styles uniquement depuis la feuille du thème) ; les blocs n'utilisent que des classes `cms-*` définies dans `@sport-cms/themes` (`BLOCKS_CSS`, y compris le menu `cms-nav*` rendu au-dessus du contenu). Couleurs du thème vérifiées par `checkThemeContrast` (WCAG AA). Chaque page publiée porte un **ETag fort** (SHA-256 du HTML exact servi, entrée de cache incluse) : `If-None-Match` correspondant (comparaison faible : un préfixe `W/` est ignoré) → 304 avec `ETag` et `Cache-Control: no-cache` conservés, jamais de corps.
- Base de données (`@sport-cms/db`) : `openDatabase(chemin)` puis `migrate(db)` ; `createTestDatabase()` dans les tests. Dates en entier, millisecondes depuis l'époque Unix (`integer(…, { mode: "timestamp_ms" })`), fixées par Drizzle (`created_at`, `updated_at`) ; JSON en texte (`text(…, { mode: "json" })` typé par `$type`) ; booléens en 0/1. Une migration commitée ne se modifie plus : on en génère une nouvelle, en deux temps (*expand / contract*) pour qu'une version N-1 tourne encore sur la base migrée. Le journal d'audit s'écrit avec `writeAudit(db, entrée)` de `@sport-cms/db` (actions sensibles, en append-only ; `actorId` absent pour le système ou une tentative anonyme).
- Authentification (`apps/server/src/auth`) : Better Auth (adaptateur Drizzle/SQLite, email + mot de passe) sur les tables `user`, `session`, `account`, `verification` de `@sport-cms/db` (champs du schéma Better Auth, générés par son CLI, adaptés aux conventions ; `user.role` est un champ additionnel refusé en entrée, valeur par défaut `member`). `createAuth({ db, baseUrl, secretKey, logger })` construit l'instance (le secret est `SECRET_KEY`, encodé en base64) ; `authRoutes({ auth, db, logger, limits? })` l'inscrit dans `createApp` via le hook `routes` : `GET /api/setup` (statut), `POST /api/setup` (installation unique, sérialisée par une ligne `instance.setup` dans `settings` : compte propriétaire rôle `owner`, identité du club dans `settings` — `club.name`, `club.sports`, `club.colors` —, entrée `setup.completed` dans l'audit), `POST /api/auth/sign-in/email` (échecs journalisés `auth.sign_in_failed`), `POST /api/auth/sign-up/email` refusée (403 : les comptes sont créés par l'installation puis par l'API admin, jamais par le public), les autres chemins `POST|GET /api/auth/*` sont ceux de Better Auth (get-session, sign-out…). Cookies de session `HttpOnly`, `SameSite=Lax`, `Secure` dès que `baseUrl` est en `https:` (jamais sur localhost). Better Auth refuse, dans tous les environnements, les `POST /api/auth/*` dont l'origine n'est pas `baseUrl` quand la requête en porte les signes (en-tête `Origin`, cookies ou en-têtes fetch-metadata) : les navigateurs du site passent, un client sans aucun en-tête (curl nu) passe, mais le `fetch` de Node envoie `Origin: null` et doit porter `Origin: <baseUrl>` ; un `POST` avec corps doit porter `content-type: application/json` (la connexion accepte aussi `application/x-www-form-urlencoded`), sinon Better Auth répond 415 — le client API de l'admin (E05) enverra l'origine.
- Rôles et permissions (`@sport-cms/core`, entrée racine sans Node, utilisable par le back-office) : `ROLES` (`owner`, `admin`, `editor`, `treasurer`, `coach`, `member`), permissions en chaînes simples (`pages.edit`, `settings.manage`, `users.manage`, `modules.manage`, `finance.manage`, `teams.own` ; un module en déclare d'autres avec son manifeste), matrice `ROLE_PERMISSIONS`, `can(user, permission)` (le propriétaire a tout). Middlewares Hono de `apps/server/src/auth/middlewares.ts` : `requireUser(auth)` (401 sans session) et `requirePermission(auth, permission)` (401 puis 403) ; ils posent `user` et `session` sur le contexte (environnement `ApiEnv`) pour les handlers qui suivent.
- Navigation (`apps/server/src/navigation-api.ts`, sous `/api/navigation`, `pages.edit` requis) : `GET /api/navigation?menu=main` (entrées `{ id, label, pageId, path, url }`, ordonnées) et `PUT` qui **remplace** tout le menu (`{ menu, items: [{ label, pageId | url }] }` : exactement une cible par entrée, page existante ou URL validée par `safeLinkUrl`, 50 entrées au plus). Le site public rend le menu `main` au-dessus du contenu (`readNavigation` : entrée pointant vers une page supprimée ou non publiée, ou vers une URL refusée → ignorée) ; un enregistrement du menu vide **tout** le cache HTML, le menu faisant partie de chaque page (le tranchage par page arrive avec les dépendances d'événements, E09).
- Limitation de débit (`apps/server/src/auth/rate-limit.ts`) : fenêtre glissante en mémoire, bornée quel que soit le trafic (`RATE_LIMIT_MAX_KEYS`, éviction des plus anciennes), par adresse client : l'adresse de la socket, sauf `trustProxy` (à activer quand le superviseur ou Caddy écrase `x-forwarded-for`, que Better Auth lit aussi en production) ; appliquée à l'installation et à la connexion (`AuthLimits`, clés de test ajustables) ; le limiteur interne de Better Auth s'ajoute en production (connexion : 3 tentatives / 10 s). Les réponses 429 sont en français avec `Retry-After`.
- Back-office (`apps/admin`) : SPA Vite (React 19, Tailwind 4 via `@tailwindcss/vite`, react-router 7), construite avec `base: "/admin/"` et servie par le serveur sous `/admin` (`apps/server/src/admin.ts`, inscrit par `main.ts` via le hook `routes`) : fichiers statiques (assets hashed → cache immuable, `index.html` → `no-cache`), repli SPA vers `index.html` pour les chemins inconnus (sauf `assets/` manquant → 404), page 503 en français quand le build est absent (dev sans `pnpm build`). Le dossier du build est résolu relativement à `import.meta.url` du module qui le sert (`../../admin/dist`, valable depuis `src` sous `tsx watch` comme depuis `dist`, à la même profondeur). L'admin a sa propre CSP (`ADMIN_CONTENT_SECURITY_POLICY` : `script-src 'self'`, `style-src 'self' 'unsafe-inline'` pour les attributs `style` de React, `connect-src 'self'`, `img-src 'self' data: https:` pour les images de l'aperçu de l'éditeur, `frame-src 'self' about:` pour l'iframe `about:srcdoc` du canvas de Puck, pas de frames externes ni de formulaires externes), posée par le handler pour écraser la CSP publique — un en-tête qu'une route pose gagne sur le middleware. Son tsconfig passe en `moduleResolution: "bundler"` (paquet navigateur : pas de `node:*`, imports locaux sans extension, `lib` avec `dom`) ; `main.tsx` rend le routeur avec `basename="/admin"` (même base que le build Vite). En développement, le proxy Vite (`/api` vers l'instance) réécrit `Origin` vers l'origine de l'instance — celle que Better Auth compare sur chaque POST avec cookies ; la cible du proxy est `PORT` par défaut, ajuster `vite.config.ts` sinon.
- Écrans du back-office : liste des pages (`/pages` : créer, renommer le chemin, publier/dépublier, supprimer en deux clics, ouvrir l'éditeur), éditeur Puck (`/pages/edition?chemin=…`, hors de la coquille, plein écran : la configuration est construite depuis le même registre de blocs que le rendu public (`src/editor/puck-config.tsx`), un clic sur un composant du tiroir l'ajoute et le sélectionne (`planInsertion`, `src/editor/insertion.ts`) — dans le premier emplacement du bloc sélectionné qui l'accepte (`allow`/`disallow`), sinon juste après le bloc sélectionné si sa zone l'accepte, sinon à la fin de la page ; le glisser-déposer reste possible —, chaque bloc rendu avec des props normalisées comme le rendu public (`resolveProps`, sauf emplacements et textes riches fournis par Puck) derrière une error boundary (bloc cassé → message français dans l'aperçu), aperçu mobile/desktop via les viewports de Puck, stylé par la feuille du site (`buildThemeCss(defaultTheme)` injectée en `<style>` dans le document de l'iframe par l'override `iframe` de Puck — `syncHostStyles: false` garde le Tailwind de l'admin dehors ; à brancher sur le thème de l'instance quand il deviendra configurable), enregistrement du brouillon, publication (ignorée tant qu'un enregistrement ou une publication est en cours : jamais deux versions pour un double clic), historique avec restauration ; avec des modifications non enregistrées, restaurer ou revenir aux pages demande confirmation et `beforeunload` prévient avant de quitter), navigation (`/navigation` : libellé + cible page ou lien externe sûr — « Choisissez une page. » vérifié avant l'envoi, entrée dont la page a été supprimée signalée sous le champ Page —, réordonnancement, suppression, enregistrement qui remplace tout le menu).
- Client API de l'admin (`apps/admin/src/api`) : `fetch` même origine, JSON, cookies (`credentials: "same-origin"`) ; le navigateur envoie lui-même `Origin` sur les POST, que Better Auth exige (vérifié dans l'e2e), et un corps POST porte `content-type: application/json`. Les messages d'erreur affichés sont toujours français : ceux de l'API de l'instance (`{ error }`) sont pris tels quels, ceux de Better Auth (`{ code, message }`, en anglais) sont traduits par code (`src/api/errors.ts`, ex. INVALID_EMAIL_OR_PASSWORD → « E-mail ou mot de passe incorrect. », 429 → « Trop de tentatives… ») et jamais montrés bruts ; sinon un repli français passé par chaque appel. La session est vérifiée au chargement (`GET /api/setup` puis get-session) : instance non installée → assistant, pas de session → connexion, sinon coquille. La réponse de l'installation signe déjà le propriétaire (cookie de session) : l'assistant mène directement au tableau de bord, sans redemander le mot de passe.
- Bout en bout (`e2e/`) : tests en anglais côté code, assertions sur les textes français visibles ; non exécutés par `pnpm check` (Vitest ne voit aucun paquet dans `e2e/`), mais lintés et typecheckés avec le reste du dépôt, et lancés par `pnpm test:e2e`. L'environnement de l'instance est posé dans la config Playwright, jamais inline dans une commande shell : `DATA_DIR` déterministe (`.playwright-data/`, ignoré par Git, remis à zéro une fois par run — la config étant évaluée plusieurs fois, jamais depuis un worker) et `SECRET_KEY` générée à l'exécution. Les specs partagent une instance et tournent dans l'ordre des fichiers : `setup-sign-in.spec.ts` installe l'instance (et sature le limiteur de connexion, fenêtre glissante : le spec suivant attend qu'un créneau se libère en réessayant), puis `site-pages.spec.ts` crée une page, ajoute un bloc **en cliquant le composant dans le tiroir de Puck** (ajout au clic, plus stable que le glisser-déposer piloté), publie, vérifie le site public, puis vérifie que modifier le brouillon sans publier ne change rien. Le test d'audit lit la base avec `node:sqlite` (expérimental : un `ExperimentalWarning` s'affiche, sans conséquence).

## Processus de développement

Tout se fait sur `main`, sans sous-agents. Pour chaque étape du backlog, dans la même session : code + tests, vérification réelle des critères d'acceptation (serveur compilé, cas limites), relecture critique du diff, `pnpm check` puis `pnpm build` verts, puis commit + push et étape suivante.
